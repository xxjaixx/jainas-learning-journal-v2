When Fast Becomes Fragile: Rebuilding Student Apps with Secure Design Principles

Introduction

The rapid growth of Artificial Intelligence (AI) has transformed how software is developed. Today, developers can build functional applications within hours by using AI coding assistants that generate large portions of source code. While this dramatically increases productivity, it also introduces a dangerous misconception that if an application works, it is automatically safe. The case of the student-built organization management platform demonstrates why security and privacy cannot be treated as optional features. Although the application successfully managed memberships, event payments, and file sharing, it failed to protect the personal information entrusted to it.

Originally developed during a weekend hackathon, the platform was intended only as a prototype. However, its popularity quickly grew, and multiple student organizations adopted it for real operations. As a result, the application stored hundreds of sensitive records, including student names, student numbers, phone numbers, uploaded identification cards, GCash payment screenshots, and private conversations. Unfortunately, the developers never redesigned the prototype into production-quality software. Instead, the same AI-generated code remained in use despite handling highly sensitive information.

When one student discovered that simply changing the profile ID in the URL revealed another student's personal record, the seriousness of the problem became clear. Additional investigation revealed exposed database credentials in GitHub, unrestricted database permissions, detailed server error messages, and unencrypted HTTP communication. These weaknesses placed every user's privacy at risk and violated fundamental secure software development practices.

What Went Wrong?

The primary failure was treating a hackathon prototype as production software. AI coding assistants are excellent tools for increasing development speed, but they generate code that prioritizes functionality rather than security. The developers accepted the generated code without performing proper security reviews, penetration testing, or code auditing.

The application also relied on "security through obscurity." The team assumed that because users did not know the internal URL structure, nobody would attempt to modify URLs manually. This assumption proved false. Any user could simply change the profile number and immediately access another student's personal information because the application never verified ownership of the requested data.

Equally concerning was the accidental exposure of database passwords and API keys inside a public GitHub repository. Once secrets become publicly available, attackers can connect directly to databases or abuse third-party services. Even if the credentials are later removed, Git history preserves earlier commits unless they are completely rewritten.

Secure Design Principles Violated

1. Least Privilege

Every account had broad database read permissions. Instead of allowing users to access only their own information, the system granted excessive privileges. The Principle of Least Privilege requires every user, application, and service to operate with only the minimum permissions necessary to perform its task.

2. Fail Securely

When errors occurred, the application displayed complete stack traces to every visitor. Error messages should never reveal internal implementation details because they provide attackers with valuable information about application structure, database technologies, and server configuration.

3. Defense in Depth

The application depended on a single weak assumption that hidden URLs would remain undiscovered. Proper security requires multiple independent layers such as authentication, authorization, encrypted communication, input validation, monitoring, and logging. If one layer fails, additional protections should remain in place.

4. Secure by Default

The application used plain HTTP instead of HTTPS. Database credentials were stored directly inside source code, and debugging remained enabled in production. A secure application should always begin with safe default settings rather than expecting developers to manually enable security later.

5. Complete Mediation

Every request must be verified before access is granted. In this case, the application authenticated users during login but never checked whether they actually owned the profile they requested afterward. This allowed unauthorized viewing of sensitive information simply by modifying URLs.

Short-Term Containment (First Hours and Days)

The first action should be taking the application offline to prevent additional exposure while an investigation begins. Every compromised credential, including database passwords and payment API keys, must be revoked immediately and replaced with new secure credentials.

Developers should remove secrets from GitHub history, force password resets for administrator accounts, enable HTTPS, disable debug mode, and implement proper authorization checks before restoring public access. A security assessment should also determine whether any unauthorized access occurred.

Users whose personal information may have been exposed should receive immediate notification. Transparency helps maintain trust and allows affected individuals to take precautionary measures if necessary.

Long-Term Design Improvements

To prevent future incidents, security must become part of the development lifecycle rather than an afterthought. Authentication should use secure session management, while authorization must verify ownership for every request. Role-Based Access Control (RBAC) should limit permissions according to user responsibilities.

Sensitive information should always be encrypted during transmission using HTTPS and protected at rest using strong encryption methods. Secrets such as database passwords should never appear inside source code but instead be stored using environment variables or secure secret management services.

Regular penetration testing, automated vulnerability scanning, dependency updates, and code reviews should become standard development practices. Logging and monitoring should detect suspicious activities before they become serious incidents.

Developer Responsibilities Under RA No. 10173

The Philippine Data Privacy Act of 2012 (RA No. 10173) requires organizations and developers to protect personal information through appropriate organizational, physical, and technical security measures. Student numbers, phone numbers, identification cards, payment screenshots, and private messages all qualify as personal information that deserves protection.

As developers, we have an ethical and legal responsibility to design systems that respect user privacy from the very beginning. Ignoring secure design principles may expose users to identity theft, financial fraud, reputational damage, and unauthorized surveillance. Compliance with RA No. 10173 means implementing privacy by design, limiting data collection, protecting stored information, and responding responsibly when security incidents occur.

Reflection

This case clearly demonstrates that software development is not only about delivering features quickly but also about protecting the people who trust us with their information. AI coding assistants are powerful tools that can dramatically reduce development time, but they cannot replace professional judgment, security testing, and responsible engineering practices.

If I were rebuilding this application, I would integrate security into every phase of development instead of adding it after deployment. Every design decision—from authentication and authorization to encryption and secret management—would prioritize user safety. Secure Design Principles such as Least Privilege, Defense in Depth, Complete Mediation, Fail Securely, and Secure by Default would guide every implementation decision.

Ultimately, shipping software quickly should never come at the expense of privacy and security. The trust users place in developers is far more valuable than winning a hackathon or releasing an application ahead of schedule. As future IT professionals, we must ensure that every system we build respects both the people who use it and the legal responsibilities established by RA No. 10173.
